# 打字練習（英打／注音鍵位）

給國小學生的鍵盤指法練習工具。參考「校園打字 GAME」（tgame.eduweb.com.tw）的課程骨架，
但題庫、程式與判分方式都是自己寫的。

## 關卡編排

中英兩套對稱，都是「從基準列出發，一次只加一列」：

| 關 | 英打 | 注音鍵位（第②批） |
| --- | --- | --- |
| 1 | 基準列 ASDF JKL; | 基準 ㄇ 列 |
| 2 | 基準列 + 下排 ZXCV | ㄇ + ㄈ 列 |
| 3 | 基準列 + 上排 QWER | ㄇ + ㄆ 列 |
| 4 | 三列混合 | ㄇ + ㄅ 列（數字列） |
| 5 | 數字列 | ㄇ+ㄆ+ㄈ 混合 |
| 6 | 全部按鍵（含 Shift 大寫） | 全部注音 + 聲調 |

每一關的題目分兩段：前段 `drills` 練鍵位、後段 `words` 是只用該關教過的字母
組成的真單字，讓孩子知道學這些鍵可以拼出什麼。

### drill 段保證把該關的新鍵全部練到

🕳️ 題庫每關寫了 20 幾題，但一關只出 6 題 drill。**純隨機抽的話會漏鍵**——
2026-09-02 跑 300 次模擬，教 QWER 的第 3 關平均漏掉 6.8 個新鍵、最壞漏 11 個，
孩子整關打完有可能一個上排的鍵都沒碰到，而那一關的存在意義就是教上排。

現在 `engine.js` 的 `pickCovering()` 用貪婪法選題：每輪挑「能補上最多還沒練到的鍵」
的那一題，蓋完才隨機補滿名額。每一關標了 `focusRows`（本關新教哪幾列），
第 4、6 關是複習關留空、不強制。

修完的實測：第 1、2、3、5 關**平均漏 0.00、最壞漏 0**，題數仍維持原本的設定值。
第 2、3 關的題庫各補了 5 題「下排／上排相鄰兩鍵」的配對題，讓 6 個名額蓋得完整排。

## 過關方式：星等，不是及格線

打完就有 1 顆星，正確率 ≥ 90% 給 2 顆，又準又快給 3 顆。

指法練習的重點是把手指位置練到不用想，不是逼低年級追速度。用及格線的話，
慢的孩子會卡在同一關過不去；用星等，每個人都走得完，想追求的人有得追。

速度標準（第 3 顆星）定在各關 8～14 WPM，定義在 `js/engine.js` 的 `WPM_TARGET`，
**再乘上年段係數**（`GRADE_FACTOR`，三年級 0.7、六年級 1.15）。年級直接從班級號碼
第一碼推（`601` → 六年級），推不出來就用 1.0。三年級手小、還在認鍵，
六年級多半打過兩年了，同一條線對兩邊都不準。
第一次敲鍵才開始計時；換題動畫與超過 5 秒的停頓不列入速度，避免老師講解或學生舉手
讓 WPM 被拉低。自由練習固定是一般題數的 3 倍，不計時也不計星星。

## 「注音鍵位」目前指什麼

第②批預定做的是**實體鍵位與手指練習**：輸入法保持英數模式，程式依
`KeyboardEvent.code` 把實體按鍵換算成 ㄅㄆㄇ。這樣不受作業系統輸入法組字狀態影響。

它不等於完整的中文輸入練習；注音組合、聲調、候選字選擇、詞句輸入是另一個模式，
需要另外處理 IME composition event。介面與文件在完成該模式前都稱為「注音鍵位」，
避免讓學生誤以為已經包含選字練習。

## 六個「電腦教室現場」守門

這些狀況都是**不會報錯、畫面也沒反應**的，孩子只會覺得電腦壞了或自己笨：

| 狀況 | 程式怎麼處理 |
| --- | --- |
| 輸入法停在注音 | `keydown` 收到的鍵名是 `Process` / `Unidentified`，跳提示教他按 Shift 切換 |
| Caps Lock 亮著 | 按對鍵卻打出相反大小寫時，跳提示叫他關掉 |
| **忘了按 Shift** | 第 6 關要打大寫，按成小寫會一直錯、游標卡在原地。用 `e.code` 比對他按的實體鍵，是對的就跳提示教他壓 Shift |
| **用 Caps Lock 蒙混** | 第 6 關教的是「壓住 Shift 打大寫」，開著 Caps Lock 一樣判對但練到錯的手法。判對不變，只是講一聲 |
| **習慣性按退格** | 引擎是「打錯不前進也不退」，Backspace 本來被整個丟掉、按了毫無反應。改成告訴他不必退格 |
| 瀏覽器擋網站資料 | `localStorage` 存取失敗不會中斷遊戲，只是這次成績不會被記住 |

> 🕳️ 忘了按 Shift 這一條是 2026-09-02 補的。在那之前**完全沒有任何提示**——
> 實測第 6 關第一題 `A1`，按小寫 `a` 的結果是正確率掉到 0%、游標卡住、畫面靜默。
> 這在孩子眼裡跟 Caps Lock 那個情境一模一樣，但只有一個有守門。

## 成績同步到雲端

進度有兩層，**下面那層永遠都在**：

| 層 | 存在哪 | 什麼時候有 |
| --- | --- | --- |
| 本機 | `localStorage`，key 是 `typing.progress.v1:<班級>-<座號>` | 一定有 |
| 雲端 | Firestore `typingScores` collection | 有網路、而且是從網站上開的時候 |

孩子練習的時候只跟本機那層打交道。雲端是事後同步的，**傳不上去不影響任何事**——
成績照樣記著，排進佇列，下次連得上自動補送。

### 為什麼另開一個 Firebase 專案

成績走 **`lotes-typing-practice`**，不是這個 repo 其他專案用的 `study-b2e59`。

一個 Firestore 資料庫只能有一份安全規則檔，而 `study-b2e59` 那份是班級作品牆／
AI 音樂 MV／儀表板三個專案共用的——部署時整份覆蓋。成績另開一個專案之後，
改這裡的規則永遠碰不到那三個。

（同一個專案開第二個資料庫也可以做到隔離，但那需要 Blaze 付費方案。）

### 學生端不載 SDK，老師端才載

這是刻意的分野，改的時候不要抹掉：

| | 學生端 `js/cloud.js` | 老師端 `js/teacher.js` |
| --- | --- | --- |
| 怎麼連 | `fetch` 打 Firestore REST API | Firebase SDK（gstatic CDN）|
| 為什麼 | 守住「零 CDN、隨身碟雙擊就能開」 | 列全班需要 Google 登入，自己實作 OAuth 不划算 |
| 斷網時 | 照常練習，成績排隊等補送 | 本來就沒東西可看 |

### 安全規則擋了什麼

規則在 `firestore.rules`（這個資料夾裡，跟程式碼放一起）。學生端不登入，
所以寫入是開放的，安全**完全**靠 schema 驗證：

- 欄位多一個少一個都拒絕，型別、範圍全部檢查
- **文件 ID 必須等於「班級-座號-關卡」**——這是最重要的一道，
  沒有它任何人都能把成績寫到別人的位置上
- 成績只能往上覆蓋（星等 → 正確率 → 速度依序比較），失常一次不會洗掉好成績
- `get` 開放但 `list` 只給老師：學生換電腦能拿回自己的星星，但沒有人能撈走全班
- `updatedAt` 一律用伺服器時間，前端送什麼都不算

> ⚠️ 班級座號沒有驗證，孩子理論上可以填別人的座號。以國小電腦課的現場來說
> 這個風險可以接受，真的遇到再加登入——資料結構已經預留位置。

### 部署規則

規則**不會**跟著 GitHub Pages 自動部署，改完要手動推：

```powershell
firebase deploy --only firestore:rules -P typing --config firebase.typing.json
```

`-P typing` 指向 `.firebaserc` 裡的別名，`--config` 指向只含這份規則的設定檔。
兩個都要帶，少一個就會推到 `study-b2e59` 去。

### 老師端

網址是主頁旁邊的 `teacher.html`。用學校 Google 帳號登入之後可以看全班進度表
（座號 × 六關的星等）、匯出 CSV、清空某個班級。

**老師端要從網站上開**，不能用本機檔案直接開——它需要 `firebase-config.js`，
那個檔是 GitHub Actions 部署時才生成的。

## 進度綁的是學生，不是這台電腦

電腦教室的機器是共用的，孩子每週不一定坐同一台。進度若只存一個 `localStorage` key，
**下一節課的孩子一坐下就看到上一個人的星星，自己的不見了**。

所以進場先填班級座號（頂端那顆 👤 按鈕，沒填會自己彈開），
進度的 key 是 `typing.progress.v1:<班級>-<座號>`。沒填照樣能練，記在 `guest` 名下。

這個欄位也正是第④批寫 Firestore 要用的身分——先在本機做掉一半，
不必等雲端那一步。

## 視覺：可愛，但不能蓋掉教學功能

畫面是一片天空，卡片是浮在上面的雲，按鍵是圓潤的糖果鍵帽。

吉祥物「小鍵」**本身就是一顆鍵帽**——這個工具從頭到尾在講鍵盤，
吉祥物不該是隨便貼上去的動物。它有四種表情（平常／開心／嚇一跳／星星眼），
打對打錯會跟著反應，台詞同一情境內隨機挑，免得整堂課聽到同一句。

裝飾可以加，但這兩件事是教學功能不是美術，不能被蓋掉：

1. **手指配色**（鍵帽頂端那條色帶）——孩子靠顏色認「這顆鍵歸哪根手指」
2. **目標鍵的打光**——畫面上最亮的東西必須是「現在要按的那顆」

彩帶和小星星都是純 CSS 做的，沒有為了這個去載 confetti 套件。

## ⚠️ 改 CSS 前先看這個

這個專案踩過**兩次**同一種特異性陷阱，兩次都是「顏色安靜地失效、沒有任何錯誤訊息」：

| 位置 | 錯誤寫法 | 後果 |
| --- | --- | --- |
| 鍵帽手指色帶 | `.kb-key[class*="finger-"] { border-top: 3px solid transparent }` | (0,2,0) 壓過 `.finger-L5` (0,1,0)，整組手指配色變透明 |
| 吉祥物眼睛高光 | `.m-glint { fill: #fff }` | (0,1,0) 被 `.m-eyes circle` (0,1,1) 壓成深色，眼睛死掉 |

規則：**形狀（寬度、有無）寫在基底類別，顏色寫在修飾類別**，
而且修飾類別的特異性不能比基底低。兩處都已在原地留了註解。

### 版面尺寸由兩個變數驅動

鍵帽邊長與題目字級是 `:root` 的 `--kb` / `--ch`，斷點只改這兩個值，
不要回頭去改每一條規則。三組斷點的**順序不能調換**：
`min-width` 先放大，`max-height` 最後壓回來（`1600×768` 這種「寬但矮」的
教室螢幕會同時命中兩組，後面那組要贏）；而 `max-height` 那組一定要帶
`and (min-width: 901px)`，否則手機那種「又窄又矮」的會被它蓋掉、鍵盤爆寬。

實測值（2026-09-02）：

| 螢幕 | 修正前 | 修正後 |
| --- | --- | --- |
| 1265×710 筆電 | 頁面高 779，**手指圖例整條掉在首屏外** | 頁面高 710，圖例底部 684，剛好不用捲 |
| 1920×1080 教室機 | 內容寬固定 1000，左右各空 460，鍵帽 43px | 內容寬 1440，鍵帽 60px、題目 44px |
| 375×812 手機 | — | 鍵帽 37px，頁面無橫向捲軸 |

提示條（`.notice`）也改成 `position: fixed` 浮在畫面上方。它原本在版面流裡，
一跳出來就把下面全部往下推——正是把手指圖例擠出首屏的那一下。

## 四個會自己吵的資料檢查

改題庫或鍵位表時，這些檢查會在載入時跑，出問題直接在畫面上跳提示：

- `keymap.js` — 大千式的 37 個注音必須各佔一鍵，多、少、重複都會被抓出來。
  大千式是「直行」排的：`1/q/a/z` 直下來是 ㄅㄆㄇㄈ，`2/w/s/x` 是 ㄉㄊㄋㄌ，
  依此類推剛好填滿 37 個，這個性質就是最好的驗證。
- `levels-en.js` — 每一關的題目不能用到該關還沒教的鍵。
- `levels-en.js` — **沒教過 Shift 的關卡不能出要按 Shift 的題目**（`allowShift`）。
- `levels-en.js` — **`focusRows` 裡的字母／數字鍵都要在 `drills` 出現過**，
  否則那顆鍵這一關等於沒教到，而且 `pickCovering` 會默默地蓋不完。

> 🕳️ 後兩道是 2026-09-02 補的，兩道都有實際抓到東西。
>
> 第 5 關原本的 `1+2=3` 和 `50%` 要按 Shift，但 Shift 是第 6 關才教的。
> 舊的檢查把 `upper` 也當成合法字元，所以它一路過關——檢查通過、畫面正常、
> 孩子卡在一顆沒人教過的鍵上。13 個單字抽 4 個，實測**有 54% 的機率會抽中**。
> 那兩題已經拿掉。
